# SliderSorter —— UI / 组件 / 布局改进方案

> 基线：`029fa88`（2026-09-22）
> 范围：`src/SliderSorter.Wpf` 的界面层。不涉及 Core 层逻辑与分组文件格式。

---

## 0. 总体判断

这套 UI 的工程纪律**远高于同类桌面工具的平均水平**。通读后没有发现常见病症，以下几点是已经做对的，**不应在本次改进中被削弱**：

| 已做对的事 | 证据 |
|---|---|
| 视图内零硬编码颜色 | `grep 'Foreground="#\|Background="#\|Fill="#'` 在 `Views/` 与 `Themes/` 下无命中 |
| 配色有机器验证 | `tools/verify_contrast.py` 按 WCAG 2.1 逐对断言，26 个色板键 |
| 主题覆盖有机器验证 | `tools/verify_theme.py` 检查窗口是否显式套 `AppWindow`、两套色板键集合一致 |
| 五语言键一致 | `tools/verify_l10n.py`，477 键 × 5 语言 |
| 多语言多尺寸不溢出 | `tools/layout-probe` 按 5 语言 × 2 主题 × 3 档尺寸（1000×720 / 1240×820 / 1440×900）离屏排布断言 |
| 空状态、禁用原因都有交代 | `EmptyStateText` 样式族；搬运按钮 `ToolTipService.ShowOnDisabled` + 动态原因文案 |
| 色盲友好第二通道 | 未保存态 = `B.Warn` 底色 + 圆点徽标 + 文案后缀（`SaveButtonLabel`） |
| 取消菜单栏后键盘路径完整 | `Ctrl+1..4` / `Ctrl+S` / `Ctrl+Z` / `Ctrl+,` / `F1` |

**因此本方案的重心是「收敛」而非「翻新」**：问题不在于做错了，而在于正确但重复的实现积累了维护面。

## 1. 当前 UI / 交互体验的主要问题

### 1.1 核心数据模型（先厘清这一条，后面全依赖它）

> **一次扫描，两份独立成果，各自可重入。**

```
                 ┌─→ 成果 A：分组（内存 Store）────────→「保存分组文件」写出 SliderGroups\*.xml
   扫描 ─────────┤
                 └─→ 成果 B：冲突清单（Settings.OutputChoices）→「写入 BodySlide…」写出 BuildSelection.xml
```

- 两者**共享同一个前置**（扫描），但**不是上下游阶段**。
- 冲突清单源自"哪些服装写同一个 `.nif`"，与"有没有建组"无关——**可以在完全没有分组的情况下先处理冲突**。
- 两份成果分别落盘、分别 dirty，互不依赖对方的完成状态。

这条模型决定了：**「输出归属」（2026-09-24 前叫「输出冲突与选择」）必须保持独立页面，不得合入「分组生成」。** 详细论证见 §2。

## 2. 关于「合并输出冲突页」的专门结论（重要）

**结论：不合并。** 四个理由如下，任一成立即足以否决合并。

### 理由 1：顺序不固定，不是线性流程
冲突源自扫描结果，与分组动作无因果关系。用户可以在**建组之前、之中、之后**任意时刻处理冲突。把它内嵌成"分组流程的第 3 步"，等于强迫只想处理冲突的用户先穿过分组界面。

### 理由 2：数据不同源，合并会污染语义
| | 成果 A：分组 | 成果 B：冲突选择 |
|---|---|---|
| 数据载体 | `Store`（内存） | `Settings.OutputChoices` |
| 落盘动作 | 「保存分组文件」→ `SliderGroups\*.xml` | 「写入 BodySlide…」→ `BuildSelection.xml` |
| dirty 标记 | `Store.Dirty` | `Settings.Save()` |
| 已有守卫 | 清单驱动的陈旧文件清理 | `BuildSelectionFile.TryExport` 保留他人条目、`OutputChoice` 连续排最前 |

合并后一个页面上会同时存在两颗"保存"语义不同的按钮，用户无法判断当前操作落在哪条链上——而项目在 `MainViewModel.Save.cs` 里花的力气正是为了区分这两条链。

### 理由 3：可重入是常态（用户提出的场景）
> "用户已完成分组生成后，只想要再重新选择「输出冲突与选择」"

这是**典型工作流**，不是边缘情况：装新模组 → 重扫 → 冲突清单变化 → 回去重新指定赢家，**全程不碰分组**。可重入性要求两者在导航上平权。

### 理由 4：合并会造成真实的空间灾难
冲突页自身结构为 **5 行 Grid**：页标题+进度 / 说明 / 工具条 / **三栏（冲突组 | 候选 | 3D 预览）** / 操作行。
分组页自身为 **三栏（树 | 搬运 | 组）+ 保存行 + 日志区**。
合并即六栏或嵌套分栏，在 `MinWidth=1000` 下必然崩——`layout-probe` 会在 `1000×720` 硬拦这类回归。

### 附带结论：撤回「阶段条」
先前草案提出的 `1 选择 → 2 归组 → 3 处理冲突 → 4 写出` **阶段条本身是错误建模**（它假设了线性顺序）。已撤回。

正确的表达是「**共享前置 + 两份独立成果**」，而不是一条流程线。落地方案：

1. **两页都挂扫描状态**：分组页补一个「重新扫描」入口，两页共用"上次扫描时间 / 结果已过期"指示器。
2. **清理暗示顺序的文案**：审一遍 `Lang.*.xaml`，`L.Conflict_Intro` 等处不得出现"接下来""然后""请先…再…"。
3. **状态栏保持中立并列**：现在 `ConflictStatusText` 与输出目录并列，这个结构本身是对的，**不要**改成流程式表述。
4. **保留冲突页自己的进度读数**：标题右侧「已指定 M / N 组」表达的是成果 B 的自身完成度，与分组进度无关，**必要且正确**。

## 3. 界面视觉与交互风格改进建议

**视觉基调不改。** 暗色 Boutique 的「深灰三层表面 + 鼠尾草绿主色 + 暖米色文字」是一套自洽且经对比度验证的设计语言，换掉等于丢弃已有的门禁资产。

以下四条是在**不新增色板键**的前提下做加法（新增色板键会绕过 `verify_contrast.py` 的断言，属硬约束）：

### 3.1 建立并文档化四级字阶
现状：`PageHeading`(18) / `SettingSectionHeader`(14) / 正文(13) / `DimLabel`(13 次要)。
问题：`SectionHeader`(13 Bold) 与正文同号，只靠字重区分，三页间层级偏平。

建议固化五个语义键并加档位注释：**页标题 / 段标题 / 字段标签 / 正文 / 次要**，禁止各页自行取值。

### 3.2 高频非破坏性提示降级为内联提示条
- **保留模态**：删除组、覆盖文件、退出未保存 —— 真正需要用户停下来决策的；
- **降级为内联**：未选组、未勾选、还没扫描这类"明明可以就地提示"的。

新增 `InlineBanner`（Info / Warn / Danger 三态），复用现有 `B.AccentSoft` / `B.WarnSoft` / `B.Danger` 系键。这一刀能砍掉大部分"点确定"的机械操作。

### 3.3 状态标记统一徽标化，与文本解耦
项目已经把 ✔ 从 `Text` 里摘出来了（`OutfitNodeVM.FormatText`），但 `[组内 x/总数]` 仍是拼进字符串的（`L.Tree_InGroupBadge`）。建议一并徽标化，让"名字"与"状态"在数据层就分开——这也顺带消除多语言下字符串拼接的漂移风险。

### 3.4 补键盘可达面
- 树上 `Space` 勾选当前行（现在 `CheckBox` 不在 Tab 序内）；
- 上下键在树内移动并同步勾选态；
- 组列表切换后焦点落到列表本身。

新建 `Themes/Components.xaml`，由 `App.xaml` 在 `Controls.xaml` **之后**合并（保证 `BasedOn="{StaticResource {x:Type ...}}"` 能解析到基础样式）。

## 5. 关键页面布局优化建议

### 5.1 分组生成页（收益最大）

- **补「重新扫描」入口**（§2 第 1 条），与冲突页对齐；
- **组列表加一行轻量头部**：计数 + 一个过滤框，与左栏两个过滤框形成对称（解决 P-6）；
- **撤销提为常驻按钮**（保留 `Ctrl+Z`），「⋯」只留新建/重命名/查看/规则归组/导入/删除（解决 P-7）；
- **日志摘要条维持折叠**——它是 660 高窗口下最贵的 96 DIP，折叠是正确决策，不要动。

### 5.2 设置页（第 2 档）

- **拆分为五节，把「工作环境」提到最前**，并加一条"未配置完成"的 `InlineBanner` 引导（解决 P-3）；
- **「清理失效服装」重新归位**：从「输出设置」移出，独立成「维护」小节（位于「帮助与关于」之上），或至少与「浏览…」拉开间距并加危险色描边（解决 P-4）；
- **保留"卡片铺满"**：这是上一 commit `029fa88` 刚修对的行为，不要回退为限宽。

### 5.3 输出冲突页（第 2 档）

版式刚在 `2026-09-22` 重排过（三栏列头同行、左栏只留文件名 + 状态、完整路径进 ToolTip），**方向正确，不建议再动结构**。只做两处增量：

- 左栏加计数与已指定状态摘要；
- `BatchScopeLabel`（"对当前列出的 N 组"）改为常显——现在是窄窗口下先让位的 `TextTrimming`，而它恰恰是解释批量动作作用范围的关键。

`2026-09-24` 增量（不动上述四行三栏版式、不搬已有控件）：操作行在「全部按模组优先级」与「全部清除」中间加一颗「按模组指定…」、候选行加右键菜单、过滤框支持 `;` / `,` 分多词。**其中一处是本意的行为变更**：右键候选行原先"立刻把这一组定给它"，现在改为"选中这一行并弹菜单"（菜单第一项就是设为赢家，第二项把该模组卷入的冲突一次全交给它）；左键那个圆圈仍是即时指定，没有变。顺带修掉一条老 bug：处理器原先挂在 `MouseRightButtonUp`（Direct 路由事件）上，指针落在行内的服装名/模组名文字上时外层 Grid 根本收不到，实机表现为"右键这一行没反应"——改用 `PreviewMouseRightButtonUp` 后才对。同一份菜单**不挂在模板上、由代码手动弹**也是实机量的：挂上去之后 WPF 的自动弹在 `ContextMenuOpening` 里把项建好了却从来没开起来（`Opened` 一次没触发）。

`2026-09-25` 增量：分组头的右键菜单在三个折叠项下面加「本组按模组指定…」，弹的是底部那颗的同一份模组菜单，只是范围换成"该组卷入的那些冲突"（与左栏该分组头下面列的行一致），并在菜单第一行写明「分组：谁 · 共几组」——同一颗菜单在"全部 581 组"和"本组 67 组"之间长得一模一样，不写清楚迟早指错。走「只看某组」+ 底部那颗也能做到同一件事，但那条路要先改掉左栏的过滤、用完还得改回去。

### 5.4 规则预设页（第 3 档）

当前是单列列表 + 三个按钮，信息密度最低。建议：

- 改为左列表 / 右详情的分栏；或
- 至少在行内直接给「编辑 / 删除」图标按钮，减少"先选中再点按钮"的两步走。

## 7. 实施约束（违反会导致静默失效）

以下来自 `README.md` 与现有 CI 门禁，**属硬性要求**：

### 7.1 新增页面须同时登记三处
否则会**静默**逃过检查（这些工具原先只扫 `Views/*.xaml`，页面放进子目录不报错、只是不再被看）：

1. `tools/verify_theme.py` §6 —— 要求它被壳引用；
2. `tools/layout-probe/Program.cs` —— 按页面根宿主进窗口量；
3. `XamlCommandBindingTests.BoundTarget` —— 登记它的 `DataContext`。

### 7.2 改壳尺寸须同步两处
改 `MainWindow.xaml` 的 `MinWidth` / `MinHeight` 时，同步改：
- `tools/layout-probe/Program.cs` 的 `ShellSizes`（当前 `[(1000,720), (1240,820), (1440,900)]`）；
- `PageChromeAllowance`（当前 `64`，为标签头 + 状态栏的合计扣除）。

### 7.3 容器尺寸不得按单一语言定死
固定像素列（`Width="96"`）、`UniformGrid` 等分列都会在更长译文下静默裁掉文字，而中文窄标签恰好掩盖这类问题。用 `WrapPanel` 按内容定宽，长文本加 `TextWrapping`，单行标签加 `TextTrimming`。

### 7.4 验证命令
```bash
python tools/verify_l10n.py src/SliderSorter.Wpf   # 语言键一致性 / Core 层不得出现中文字面量 / 菜单访问键
python tools/verify_contrast.py                        # 两套色板 WCAG 2.1 对比度
python tools/verify_theme.py                           # 窗口显式套主题 / 两套色板键集合一致
```
